# CLAUDE.md

## Project Overview

**my-money-tracker** — personal portfolio tracker. Node.js/Express backend, React/Vite frontend (JSX, not TypeScript), PostgreSQL, Tailwind CSS 4. Multi-user with fully isolated data: production auth is Azure App Service Easy Auth with Google sign-in (identity read from `x-ms-client-principal-*` headers, gated by `ALLOWED_PRINCIPALS`); an allowlisted email's first sign-in auto-provisions a user via `user_identities` (one person can map several emails to one user — both of the original owner's emails point at user 1). Local dev stubs identity (`DEV_AUTH_USER_ID`/`DEV_AUTH_USERNAME`; the stub ensures the users row exists, so `DEV_AUTH_USER_ID=2` simulates a second user). `/mcp` is protected by an `MCP_API_KEY` bearer token that maps to user 1; `FinancialQueryService` methods all REQUIRE a userId and throw without one.

## Quick Start

```bash
# First time: bootstrap DB, .env files, deps, migrations (migrations seed user 1)
./scripts/setup-local.sh    # run in Git Bash (not WSL)

# Start both servers (double-click or run from any terminal)
python scripts/dev.py       # backend :3000, frontend :5173/private/

# No login locally; dev identity is stubbed in backend/src/middleware/auth.js
```

## Architecture

- **Backend**: Express 5, CommonJS, pino logging, pino-http request IDs, express-rate-limit, node-cron scheduled jobs
- **Frontend**: React 19, Vite 7, Tailwind CSS 4, Recharts (all charts), TanStack Table, React.lazy code splitting
- **Design**: "AVE Workbench" — VSCode-inspired dark workbench. CSS custom properties in `index.css`, mapped to Tailwind via `tailwind.config.js`. System fonts (UI) + Consolas (financial numbers). Primary: #297AA0, canvas: #191A1B, editor: #121314. Dense 13px UI, 1px borders, square panels. See `DESIGN.md` for full spec.
- **Layout**: Sidebar navigation (not top nav), state-based routing (no React Router in production)
- **Serving**: backend serves `backend/public/` (public landing) at `/` and the built React app at `/private` (Vite `base: '/private/'`). Azure Easy Auth gates `/private` and `/api` in production; `/` and `/mcp` are excluded.

## Key Patterns

- **API interceptor** (`frontend/src/utils/api.js`): same-origin requests (Easy Auth session cookie), retries on 5xx (once, 500ms), reloads page on 401 so Easy Auth re-authenticates
- **Shared formatters** (`frontend/src/utils/format.js`): `formatCurrency`, `formatPercent`, `formatDateDisplay`, `formatDateAxis`, `formatCompactCurrency`, `formatRelativeTime` — all components import from here, no local duplicates. Category labels in `utils/dataLabels.js`.
- **Shared UI**: `FilterTabs` (single-choice control — tab strip on desktop, dropdown on mobile; used by Balances, Settings, Accounts, Spending), `DataTable`/`DataTablePagination` (TanStack table shell — used by Balances, Accounts), `LoadingState` (all loading spinners), `useTransientMessage` (auto-clearing success messages)
- **Chart theme** (`frontend/src/utils/chartTheme.js`): `CHART_COLORS`, `GRID_STYLE`, `AXIS_STYLE`, `TOOLTIP_STYLE`, `areaGradient` — all charts use these
- **Design tokens**: CSS variables in `index.css` (canvas/surface hierarchy, ink/body/muted text, primary action blue, gain/loss semantics, hairline borders) consumed by Tailwind config. Component classes: `.card`, `.font-money`. Square panels with 1px borders, 4px radius on buttons/inputs only.
- **Multi-user scoping**: ownership lives on root tables only (`accounts`, `plaid_items`, `eth_wallets`, `salary_history`, `recurring_expenses`, `ignored_merchants`, `eth_ignored_tokens`, `eth_address_labels` — nullable there, NULL = shared builtin). Children (holdings, transactions, snapshots, trades, tax lots, eth_transfers, …) inherit via `JOIN accounts a … AND a.user_id = $n`. Mutations use `WHERE id = $1 AND user_id = $2` → foreign ids 404. Scoped model reads are fail-closed (a missing userId throws); cross-user reads use the explicit `findAllForJobs` entry points (`Holding`, `EthWallet`, `PlaidItem`) and belong only to jobs. Shared/global by design: `price_cache`, `benchmark_prices`, `security_master`, `job_logs`, `eth_method_signatures`. Auth resolves users through `user_identities` with a 5-min in-process cache and auto-provisions allowlisted emails.
- **API keys** (Settings → API Keys, `routes/keys.js` + `services/SecretsService.js`): per-user Plaid client ID/secret and Etherscan key in `user_api_keys`; shared CoinGecko/CMC keys in `app_settings` (admin-only, managed from the Server tab). AES-256-GCM encrypted with `SECRETS_ENCRYPTION_KEY` (32-byte base64); resolution is DB value → env var → null; masked statuses only ever reach the client (stored `last4`). Without `SECRETS_ENCRYPTION_KEY` the app is env-only and key writes 503. Plaid clients come from `config/plaid.js` `getPlaidClientForUser`; Etherscan keys are threaded through `EtherscanService` per request.
- **Admin panel** (Settings → Server tab, `routes/admin.js`, gated by `requireUser.requireAdmin`): user 1 is the sole admin (`users.is_admin`, seeded by migration 030, no grant UI). Shows shared market-data keys, an env overview (secrets as masked last-4 only — full values never leave the server, and `SECRETS_ENCRYPTION_KEY` reports set/valid with no last-4 at all), a view-only users list, job schedules with Run Now buttons, and health. Tab visibility comes from `/api/me`'s `isAdmin`, not from probing the admin API. Non-admins never see the tab and get 403 from `/api/admin/*` and from shared-key writes.
- **Scheduled jobs**: Plaid sync 7:30, expense sync 7:45, ETH wallet sync 7:50, exchange API sync 7:55, price updates 8:00, historical price backfill 8:10, benchmark prices (SPY/QQQ) 8:30, snapshots 9:00 (all UTC). Controlled by `RUN_SCHEDULED_JOBS`. Plaid/eth/exchange syncs resolve each item/wallet/account OWNER's credentials and skip-and-log unconfigured owners; expense sync iterates users; price/benchmark/snapshot jobs stay global. `POST /api/jobs/trigger/*` is admin-only (these jobs touch every user's data with each owner's credentials) except `price-update`, which any user may run because `price_cache` is shared and the Dashboard refresh calls it.
- **Ethereum wallets**: Etherscan V2 integration mirrors the Plaid shape (`services/EthWalletService.js`, `routes/eth.js`, `jobs/ethSyncJob.js`). Raw transfers land in `eth_transfers` (counterparty classified self/exchange/external — both sets scoped to the wallet OWNER: self from the owner's wallets UNION their `kind='own'` labels, exchange from the owner's `kind='exchange'` labels plus shared builtins seeded in migration 029, user label shadows builtin, own beats exchange), balances become a `crypto` account with an ETH holding + NULL-ticker token holdings, and activity is mirrored into `transactions` via `eth_transfer_id` with `CRYPTO_*` categories (`CRYPTO_EXCHANGE_DEPOSIT`/`_WITHDRAWAL` classify as internal transfers). Token symbols never enter `price_cache`. A txlist row's `methodId`/`functionName` ride on exactly one leg per tx: the native leg when ETH moved, else the gas leg (zero-value calls -- approve, token swaps -- emit no native leg but their calldata still originated from the wallet). Selectors Etherscan cannot name are decoded during sync (never at request time, bounded by a lookup cap and a 30s deadline) via Sourcify's signature database, then 4byte.directory, cached in the global `eth_method_signatures` including MISSES so each selector is fetched at most once ever -- but an off-shape 200 counts as a transport failure, never a cached miss. A decoded name is a low-confidence display hint (selector collisions are mined deliberately) and must never feed classification. Method capture is FORWARD-ONLY: rows ingested before migration 034 keep NULL method columns (the decode pass names stored selectors, it cannot invent them); a full re-capture requires removing and re-adding the wallet, which restarts ingest from block 0. Disconnecting with `removeData=false` detaches the account but keeps its row and name, so `addWallet` re-attaches (and un-hides) that account instead of inserting a duplicate — the account name is unique per user, and re-attaching is what preserves the history "keep data" was for.
- **NFT transfers** (migration 033): `tokennfttx`/`token1155tx` feeds land as `transfer_type` `nft`/`nft1155` legs carrying `token_standard` + `token_id`, with per-feed cursors (`last_block_nft`/`last_block_1155`, default 0 — so unlike FORWARD-ONLY method capture, 033 backfills NFTs from block 0 at the next sync). `value_wei` on NFT rows is a COUNT OF UNITS (always 1 for erc721 — the feed has no value field; the 1155 feed's `tokenValue`), never wei — a `/1e18` reader must branch on transfer_type first, and `token_decimals` is written 0 because the shared unit helpers default NULL to 18. Balance math stays fail-closed: `tokenBalanceDeltas` keys on `token_standard = 'erc20'`, so NFT legs can never leak into holdings. Feed failures are isolated per feed: a failed NFT fetch skips that feed's `deleteFromBlock` and leaves its cursor unmoved while the other feeds proceed — advancing past unfetched rows would drop them silently and forever. Etherscan emits one row per id for 1155 batches, so ordinals unbundle a batch with no extra work.
- **Exchange records** (Settings → Exchanges, `routes/exchanges.js`, `services/exchangeImport/`, migration 037): on-exchange activity never touches a tracked wallet, so it arrives as a CSV export. `exchange_accounts` is the root table (`user_id NOT NULL`); `exchange_records` inherits scope through it. One record per economic event, not per CSV line — Kraken's two trade legs (paired by `refid`) and Coinbase Pro's two `match` rows plus its `fee` row (grouped by order+trade id) each collapse into one row carrying both assets and the fee. `UNIQUE (exchange_account_id, external_id)` keys records by the event the exchange recorded, and the conflict arm is a one-directional guarded upgrade — `DO UPDATE … WHERE exchange_records.needs_review AND NOT EXCLUDED.needs_review` — so re-uploading the same export is pure duplicates while a FULLER export completes flagged placeholders without ever downgrading a complete row (in-file duplicates collapse first; Postgres refuses to update the same row twice in one statement). Resolving a review is a one-way door: it clears `needs_review`, which is the upgrade gate, so a hand-resolved partial row is "accepted", not "repairable". Rows with no native id (Coinbase Pro conversions) get a deterministic content hash. Upload is raw `text/csv`, like the holdings bulk import. **Fail-closed both ways**: an unrecognized header layout aborts the whole import with the header quoted back, and an unrecognized ROW type imports as `record_type='transfer'` with `needs_review` — never dropped, and never guessed into income or a deposit (which would enter the on-chain matching pass). Two Kraken traps: `earn` rows with subtype `allocation`/`autoallocation` are spot↔earn wallet moves, not rewards (booking them as income would count the whole allocated principal, twice), and asset codes need normalizing (`XETH`→ETH, `ZUSD`→USD, `ETH2`→ETH, `.S`/`.M`/`.F` suffixes stripped) or one position splits in two. Fixtures under `backend/tests/fixtures/exchanges/` are synthetic by rule — real exports are personal history and the repo is public.
- **Counterparty triage** (Settings → Ethereum → Needs Review, `GET /api/eth/counterparties/unreviewed`): `eth_address_labels.kind` (migration 032) makes a label mean "reviewed, with a verdict" rather than "is an exchange" — `exchange` | `external` (reviewed third party, changes nothing) | `own` (the user's untracked address; strictly user-scoped, no builtin fallback). The queue is every counterparty with no label row of any kind, minus gas rows, failed transfers, own counterparties, ignored-token transfers and contract creations — so it drains monotonically; a static hot-wallet seed can't keep up with exchanges rotating addresses, and an unlabeled one silently reads as real spending. `EthWalletService.refreshClassificationsForUser()` re-derives that owner's rows, so labeling heals all history retroactively. Badge counts material rows only (`usd_volume >= min_usd OR sent_count_valued > 0`) — a badge that can't reach zero gets ignored, which is exactly why outbound NFT legs are excluded from that OR arm (038): an NFT leg gets no mirror row, so its `usd_volume` is 0 forever and the arm — which exists to rescue a value that merely FAILED to resolve — would pass permanently, making every one-time NFT buyer material at $0. `sent_count` still reports the true outbound count for display; NFT-only counterparties stay enqueued as dust (`include_dust=true`) and the transaction itself is explained in `eth_activity`. **Traps**: (1) in `reclassifyCounterparties`' second UPDATE, `kind` is tested in the projection CASE, never the WHERE — filtering there lets a builtin `exchange` outrank a user's `external` override; (2) `upsert` takes a NULL `kind` as "keep the current verdict" (defaulting to `exchange` only on insert), because a rename sends no kind and must not silently re-vote; (3) the queue orders `material DESC` before `usd_volume DESC`, or an unpriced outbound counterparty sorts below every one-cent airdrop and pages out from under its own badge.
- **Activity layer** (migration 038, `services/EthActivityService.js` + `models/EthActivity.js`, `GET /api/eth/activity`): `eth_transfers` is per LEG, so a swap reads as three unrelated ledger rows. `eth_activity` is the tx-level explanation — exactly one row per `(wallet_id, chain_id, tx_hash)`, enforced by a UNIQUE constraint — the builder groups legs on `(chain_id, tx_hash)`, never `tx_hash` alone, because a cross-chain replay (same account, nonce and calldata on two chains) genuinely shares a hash, with `legs JSONB` netted per asset and `fee_wei` off the gas leg. DERIVED WHOLESALE: rebuilt on sync and on every classification refresh (label write, wallet add/remove, ignore-list change), same pattern as `reclassifyCounterparties`. Corrections live in `eth_activity_overrides` — a separate table precisely so the rebuild cannot erase one — and every reader COALESCEs override over derived, which also clears `needs_review` (an override IS a review). The per-leg `transactions` mirror is untouched; Spending still reads it. **Ladder** (deterministic first): `is_error` → `failed` is evaluated as a GATE, not the numbered rule 8 — a reverted send to Coinbase would otherwise pass rule 2 as a completed deposit — then 1 all-own → `self_transfer`, 2 exchange label → `exchange_deposit`/`_withdrawal`, 3 zero-address NFT legs → `nft_mint`/`nft_burn`, 4 no net movement → `contract_interaction`, 5 fungible out + different fungible in → `swap`, 6 NFT vs fungible → `nft_purchase`/`nft_sale`, 7 one-way → `send`/`receive` with `needs_review` always true. **Traps**: (1) `method_id`/`method_name` are copied for DISPLAY only and NO rule reads them — which is why `approval` is unreachable from the ladder (only the selector separates it from any other zero-value call) and is override-only, alongside `spend`, which waits on a merchant label kind; (2) rule 7 never auto-classifies spending, so an unreviewed outbound transfer is flagged, never counted; (3) NFT legs net per `(contract, token_id)` and their `value_wei` is a UNIT COUNT (033), so `legDecimals` branches on `transfer_type` before scaling; (4) ignored-token legs are filtered out of classification, so spam lands as an unflagged `contract_interaction` instead of refilling the review queue nightly; (5) an unknown `?category=` or `?needs_review=` is a 400, not a silently unfiltered feed; (6) the revert gate reads `eth_transfers.tx_is_error` as well as per-leg `is_error` — a reverted ZERO-VALUE call (failed approve, swap that reverts before any Transfer log) emits only a gas leg, and gas legs are written `is_error = false` deliberately (the fee did not fail, and the mirror and triage queue depend on that), so 038 stamps the transaction's own status on the gas leg at ingest. FORWARD-ONLY like 034's method capture: pre-038 rows are NULL and still classify `contract_interaction`; remove + re-add the wallet to re-ingest from block 0; (7) an override must target an existing activity row — readers join activity → override, so a correction against an unseen hash would be stored and invisible forever, hence the 404.
- **Multi-chain wallets** (migration 039, `config/chains.js`): one address is synced across several chains through the same feed pipeline — Etherscan V2 serves them all from one key via `chainid`, under the one global throttle (the rate limit is per key, so five chains must not multiply the request rate by five). Registry defaults: Ethereum 1, Arbitrum One 42161, Linea 59144 **on**; OP Mainnet 10 and Base 8453 **present but off** (in the chainlist, but every action there answers "Free API access is not supported for this chain" on a free key — a plan entitlement, not a missing feed). zkSync Era 324 is **absent, not disabled**: `/v2/chainlist` does not serve it at all, and Linea took its slot. `ETH_CHAINS=1` restores exact mainnet-only behavior. Cursors moved off `eth_wallets` onto `eth_wallet_chains` ((wallet_id, chain_id) PK, all five feed cursors, per-chain error slot, `unsupported_feeds`); the eth_wallets columns are **frozen, not dropped** — 039's seed reads them every boot. Failure is isolated per (chain, feed) in three flavours: transient → `FEED_SKIPPED` (retried, badges the wallet), `ETHERSCAN_FEED_UNSUPPORTED` → that feed only, `ETHERSCAN_CHAIN_UNAVAILABLE` → a verdict on the whole chain, so the remaining four feeds are marked without being called. All three freeze the cursor and skip that feed's delete. A chain whose ingest throws for any other reason (a DB blip in `bulkInsert`) is isolated the same way — its error lands on its own chain row, its cursors go unwritten, and the chains that DID land still get their reclassify/holdings/mirror rebuild; only a wholly-failed wallet throws. **Traps**: (1) the 039 seed is `DO NOTHING`, never `DO UPDATE` — migrations re-run every boot and the eth_wallets cursors are frozen, so a DO UPDATE would rewind every live chain-1 cursor at each restart, and since sync deletes its resume window first, each boot would delete and rebuild the whole history; (2) `deleteFromBlock` and the UNIQUE both need `chain_id` — block numbers are independent per-chain sequences, and `ON CONFLICT DO NOTHING` would drop a colliding cross-chain row silently rather than erroring; (3) holdings are matched by NAME, because one account now holds several `ticker='ETH'` rows and the old ticker matcher would let each chain overwrite the previous one — mainnet's names (`Ethereum`, `SYM 0xabc…1234`) must stay byte-identical or every existing holding is stranded and duplicated; (4) holdings cleanup is scoped to the chains a run actually re-derived (`holdings.chain_id`), which is what makes disabling a chain stop its sync without deleting its rows; (5) token prices are fetched per chain against that chain's CoinGecko asset platform — the wrong platform returns *unknown*, not an error, so pooling contracts reads as a pricing outage that never resolves; (6) several `ticker='ETH'` rows in one account would appear twice in `ticker_snapshots`' `ON CONFLICT DO UPDATE` and Postgres refuses that outright, so `SnapshotService.collapseDuplicateKeys` sums same-key rows before insert — keyed on the RAW ticker, matching the case-sensitive index exactly, since folding case would merge `aapl` into `AAPL` and lose a real series. Labels stay address-keyed with no chain column (an exchange is the same counterparty on every chain); `transactions.chain_id` carries the mirror's chain through (039 backfills it from `eth_transfers` for pre-#58 rows, so NULL really does mean "not on-chain"). Explorer links are keyed on `chain_id` client-side in `frontend/src/utils/chains.js`, which mirrors the registry.
- **Exchange API sync** (Settings → Exchanges, `services/exchangeSync/`, `services/ExchangeSyncService.js`, `jobs/exchangeSyncJob.js` at 7:55 UTC, migration 040): read-only keys per exchange ACCOUNT (not per user — one person can hold two Kraken accounts, and `user_api_keys` is keyed `(user_id, service)` with no room for the second), AES-256-GCM on `exchange_accounts` via the same `secretCrypto` the API Keys tab uses; writes 503 without `SECRETS_ENCRYPTION_KEY` and only the stored `last4` ever reaches the client. Migration 040 put ciphertext on the table, so `SELECT *` is now a leak: route-facing reads go through `ExchangeAccount.PUBLIC_COLUMNS` and only `findWithCredentialsForUser`/`findAllForJobs` see the encrypted columns. **The app calls READ endpoints only, enforced in code**: `krakenClient.ALLOWED_ENDPOINTS` and `coinbaseClient.ALLOWED_PATH_PREFIXES` + GET-only, so no key permission can make it trade or withdraw. Kraken auth is HMAC-SHA512 over `uriPath || SHA256(nonce || postData)` under the base64-DECODED secret (the nonce appears TWICE in the SHA256 input, and the digest concatenates as RAW BYTES, not hex); the published worked example is a real test vector and is asserted verbatim. Coinbase is an ES256 JWT with the **nonce in the HEADER**, `iss: 'cdp'` (the C# doc sample's `coinbase-cloud` is stale), `exp` 120s, and `uri` = `"METHOD host+path"` with no scheme and no query — so a paginated call signs the bare path and appends its query separately; ECDSA PEM keys only, Ed25519 is rejected by name rather than as an opaque 401. **The dedupe contract is structural**: both the Kraken CSV reader and the Kraken API reader normalize into one row shape and share `exchangeImport/krakenLedger.buildRecords`, so external_ids cannot drift and a CSV upload after an API backfill is pure duplicates; Coinbase keys `cb:<v2 transaction id>`, which is exactly the retail CSV export's ID column — including a **Convert**, which keys the OUTGOING leg's transaction id: the trade id groups the two legs but cannot key the row, because the retail CSV has no trade-id column and only an id BOTH readers can compute from their own source keeps a CSV-after-API upload a no-op. The cost, identical on both readers: a page budget between the legs imports each alone and flagged, the outgoing one on the canonical id (upgradeable in place), the incoming one as a second flagged half-row. `exchange_records.source` ('csv'|'api'|NULL for pre-040) is provenance only and takes no part in the conflict key or the `needs_review` upgrade guard. **Traps**: (1) Kraken's REST and CSV vocabularies are DIFFERENT — `earn` does not exist in REST (it is `staking`/`reward`/`transfer` with spot↔staking subtypes) and seven response types (`spend`, `receive`, `reward`, `conversion`, `nfttrade`, `nftcreatorfee`, `custodytransfer`) cannot even be requested as a `type` filter, so the feed is never filtered by type; (2) Kraken answers HTTP 200 with a populated `error` array on failure, so a 2xx is not success; (3) `Ledgers` returns NEWEST first, so a page budget truncates the OLD end — the cursor is `{newestTime, pendingStart, pendingEnd, pendingOffset}`, not a single watermark, or a partial backfill marks itself complete and strands everything older forever; when a whole budget fits inside the window's TOP second, shrinking cannot progress at all, so the window is kept and `pendingOffset` carries the offset reached (the old clamp to `end-1` progressed by stranding the rest of that second); (4) `start` is EXCLUSIVE and two rows can share a timestamp, so resume rewinds an hour and lets the upsert absorb the overlap; (5) the ON CONFLICT upgrade is one-directional so it CANNOT fill a CSV-first row's missing tx_hash/address — `ExchangeRecord.backfillChainDetails` does that with a separate strictly-additive COALESCE UPDATE that never touches `needs_review`; (6) v2 money hashes are `{amount}` and v3's are `{value}`, and reading one spelling silently yields a zero balance that reconciles as "the ledger is wrong". After every sync, per-asset balances derived in SQL (exact NUMERIC, never floats: base + quote − fee) are compared to the live Balance/accounts endpoint and a gap sets `last_sync_status='balance_mismatch'` — except while `backfill_pending` (a partial history says nothing about the parser) or while the LIVE side is itself incomplete (a truncated Coinbase account walk reads every unenumerated portfolio as zero), where reconciliation is skipped outright. Coinbase's per-account walk also carries a `done` set beside `pending`: `pending` says where the unfinished accounts stopped but not which finished, so more wallets than page budget re-walked the completed ones every pass and converged never. Both clients strip `config`/`request` off transport errors before they propagate (the Kraken `API-Key`/`API-Sign` and the Coinbase `Authorization: Bearer` live there and pino's `err` serializer copies them), with `redact` paths in `config/logger.js` as the second line. A per-account in-flight Set refuses a Sync Now that overlaps the nightly job — single-process assumption, noted at the guard. Clearing a credential needs no encryption key (it NULLs ciphertext), and a server-wide `SECRETS_NOT_CONFIGURED` writes no per-account status. Withdrawal/deposit destinations come from Kraken's `WithdrawStatus`/`DepositStatus` joined on `refid` (the Ledgers feed has neither) and Coinbase's `network.hash` + `to.address`; they feed forgotten-wallet discovery (#72). A failed sync writes its status and leaves the cursor untouched.
- **Balance reconciliation** (migration 042, `services/EthReconciliationService.js` + `models/EthReconciliation.js`, `GET /api/eth/reconciliation`): sync starts every feed at block 0, so the stored ledger is genesis-complete and the balance derived from it must equal what the chain reports. One `eth_reconciliation` row per `(wallet, chain, asset)` — `asset_key` is `'ETH'` or the token contract, NOT NULL because it is the upsert target and a NULL never conflicts. Derived in exact `NUMERIC(78,0)` base units, never floats, never pre-scaled: `EthTransfer.nativeBalanceDeltas` is inbound native+internal − outbound native+internal − gas, with **gas as its own term** (a gas leg's from is always the wallet, so on a self-send an inbound arm would credit back the fee), failed transfers excluded but **their gas leg kept** (a revert still burns it — which is why gas legs are written `is_error=FALSE`), and NFT legs absent entirely (their `value_wei` is a unit count, 033). Written last in `_syncWallet` and wrapped in a catch: the audit is a VERDICT ON the sync, never a gate in front of it. **Report, never correct** — holdings still come from the live balance; overwriting the derived number would hide the bug. **Skip rather than guess**: a chain that errored, is unreadable, has never synced, or whose `unsupported_feeds`/`skippedFeeds` cover a feed the asset needs (`normal`+`internal` for ETH, `token` for ERC-20) records `status='skipped'` with a reason and NULL live/delta, and spends no Etherscan request. ETH gets **no tolerance band** (a nonzero delta is a hard signal and sets `reconciliation.needs_review`, which the Ethereum tab badges); tokens get a dust band (1e-8 of a unit, or 1ppm of the live figure, both exact BigInt) because rebasing and fee-on-transfer contracts drift with no transfer to record — so token drift is reported but never badged. **Traps**: (1) live ETH is threaded from `refreshHoldings.liveWeiByChain`, which already fetched it — a second `action=balance` per chain would double the audit's cost against the one global throttle; (2) `tokenbalance` is one request per (chain, contract), so lookups are capped at `MAX_TOKEN_LOOKUPS` per wallet per sync and rotate least-recently-checked-first, with the deferred ones stored as `skipped/lookup_budget` rather than silently omitted — and `checked_at` (NULLABLE, NULL = never compared, sorts first) advances ONLY for a compared status (`match`/`dust`/`mismatch`/`unavailable`), never on a skip write, or the deferred tail would take the run's LATEST stamps (one statement per asset) and starve permanently; a missing key is its own reason (`no_api_key`), since `lookup_budget` promises a later sync that cannot happen, and a chain absent from `liveWeiByChain` spends no token lookups at all (its ETH read already failed this run); (3) `pruneMissing` keys on `chainId:assetKey`, not the bare address, and is scoped to the chains the run actually walked — a disabled chain keeps its last verdict, or "chain off" would read as "chain passed"; (4) a token with a NEGATIVE derived balance is audited rather than dropped (holdings drop it) — it is the loudest evidence of a missed inbound transfer, and a derived ZERO is kept too until a previous run's verdict says the chain agreed it was zero (`derived zero` is the ledger's own claim, and the ledger is what is under test; a zero-derived token never seen before stays a blind spot); the audit's deltas render at FULL precision (`formatExactUnits`) — the 6-digit default prints a sub-microether mismatch as "0 ETH off" beside two identical figures; (5) an asset whose write fails still counts as written, or a transient error would let the prune delete it; (6) every read joins `eth_wallets` on `user_id`, throws without a userId, and filters out ignored tokens live (ignoring a token must take effect immediately, not at the next nightly sync); the route's summary takes the same `wallet_id` as the feed, so headline counts never total every wallet above wallet-filtered rows; (7) the stored-state fallback in `chainGates` (used when a caller passes no `chainResults`) is fail-closed — `CHAIN_UNAVAILABLE` aside, ANY `error_code` skips the chain as `chain_error`, because `eth_wallet_chains` has collapsed the per-feed detail and an unrecognised code means a hole of unknown shape.
- **Builtin label pack** (migrations 035/036, `backend/scripts/generate-label-seed.js`): `eth_address_labels` carries `source` (`user` | `builtin` | `eth-labels`) and `confidence` (`high` | `low` | NULL on user rows). 036 seeds 5,129 addresses scraped from the eth-labels dataset (4,740 `exchange`, 389 `external`) as `user_id NULL, source='eth-labels', confidence='low'`; regenerate both artifacts (`backend/data/builtin-address-labels.json` + the migration) from the 21MB dump, which is NOT committed. `external` is the dataset's `dex` tag plus the generator's demotion list (`MERCHANT_NAME_RE`: payment processors, fiat on-ramps, `…: Deployer` rows) — paying a gateway is spending, and a wrong `exchange` deletes it from cash flow while a wrong `external` only costs a queue entry. Neither provenance column votes: precedence is still user-shadows-builtin and own-beats-exchange, and the label forms (Settings → Ethereum, plus the Crypto page's inline Label button) carry a verdict selector so a wrong pack row is correctable in two clicks. Seeding is not a reclassification: the triage queue reads labels live and drains the moment the migration commits, but `eth_transfers.counterparty_exchange` is denormalized and only heals at the next wallet sync or label write (`refreshClassificationsForUser`) — no migration calls it. **Traps**: (1) 035 deliberately has NO `source` backfill — 029 runs earlier each boot and moves the only global-but-`'user'` rows onto user 1, so a "global means builtin" UPDATE would match nothing it was written for while sitting one predicate away from restamping the whole scraped pack; (2) the seed is `ON CONFLICT (address) WHERE user_id IS NULL DO NOTHING`, never DO UPDATE, so a re-boot cannot re-stamp a name or kind the user corrected, and 029's hand-verified rows (inserted first, `confidence='high'`) win every overlap; (3) `findAllForUser` hides pack rows from the Settings management list (filtered outside the DISTINCT ON, after shadowing resolves) — 5k scraped rows would bury the user's own labels; `findByAddress` and classification still see them, and an override of a packed address is a user row, so it still lists.
- **Unified crypto ledger** (#63, `models/CryptoLedger.js` + `routes/crypto.js`, `GET /api/crypto/ledger`, `/ledger/summary`, `/ledger/export`; UI in `components/CryptoLedger.jsx`, the Crypto page's Transactions tab): `eth_activity` UNION `exchange_records` as ONE chronological stream — the milestone's payoff surface, and the first consumer of 041's matches, 042's audit and 043's dated dollars. **No migration**: it is a read-side join over what 037/038/041/043 already store. Ordered by TIME and nothing else (`block_number` is a per-chain sequence since 039 and a venue record has no block), with `(source, row_id)` as the tiebreak because neither id is unique across the union and a non-total ORDER BY lets LIMIT/OFFSET repeat one row and drop another. `record_type` is mapped onto the activity vocabulary in ONE place (`recordCategory`) so a single `?category=` answers for both sources; `trade`/`conversion`→`exchange_trade`, `deposit`→`exchange_deposit` (both sides agree on the word), plus two ledger-only values, `fee` and `exchange_transfer` — the latter is deliberately NOT `self_transfer`, which would assert both ends are the user's when the import could not tell. **The fold is 041's, not this file's**: `exchange_matches` already decided which record is the same money as which transaction, with evidence and a user verdict, so the ledger reads that table rather than re-deriving a second matcher that would disagree with the first. Both of 041's shapes fold — a record into its on-chain row, a counter record into its pair's primary — and either way the movement renders once. USD comes from `eth_activity.usd_value/usd_fee/usd_basis` (043, at-the-time), never recomputed; a venue row is only in dollars when the venue itself quoted it in dollars, which is `exact`, and every other case is `unpriced` rather than $0. **Traps**: (1) a folded record is suppressed from `exch`, so the `source`/`category`/`exchange_account_id` filters each carry a second arm testing the host's `match_category`/`match_account_id` — without it the filter DROPS the event from every view rather than narrowing to it, and the mismatch is the normal case (the venue files a "withdrawal" for the transaction the wallet files as a deposit); (2) the row's `needs_review` ORs the folded half's, or a flagged record folded into an explained row silently leaves the queue while still being unexplained; (3) `jsonb_build_object` emits a NUMERIC as a JSON *number* and node-pg parses jsonb with `JSON.parse`, so every amount inside the match object is cast `::text` — otherwise a folded quantity below 1e-6 renders in exponent notation and one above 2^53 loses digits; (4) the row id keys on `(chain, hash, wallet)`, never `eth_activity.id` — that table is DELETEd and rebuilt on every sync and every label write, so an id-keyed client loses the row it had open the moment a relabel reclassifies history (the same reason 041 keys its verdicts that way); (5) the match object carries explicit `verdict_exchange_record_id`/`verdict_counter_record_id`, because a venue pair shows the COUNTER record while the verdict is keyed on the primary, and inferring that client-side gets it backwards; (6) `summary.exchange_count` counts RECORDS, folded ones included, because it sits beside Settings' per-account `record_count`; (7) legs carry base units + their scale so the client renders through the SHARED `formatTokenUnits` (BigInt end to end) instead of a second formatter; (8) CSV export is columns, not a rendered sentence (a description cannot be summed), `usd_value` is left EMPTY when unpriced rather than written 0 with `usd_basis` beside it to tell a real zero from a gap, text cells built from chain-authored names are prefixed when they open with a formula character, and truncation at the 50k cap is written INTO the file — the export is an `<a href>` download, so a browser discards the `X-Row-*` headers. The needs-review badge takes no materiality floor (unlike counterparty triage): every row is resolvable in two clicks, so the count already reaches zero. Review actions reuse existing endpoints only — override/revert on `/api/eth/activity/override`, confirm/reject a pairing on `/api/exchanges/matches/verdict`, label on `/api/eth/address-labels` (which reclassifies all history, draining many rows at once), resolve on `/api/exchanges/:id/records/:recordId/resolve`. Three independent incompleteness signals are surfaced rather than averaged into one: 042's native balance drift (a transfer is missing), 043's `GET /api/eth/prices/unpriced` (the dollars are absent, not zero), and an exchange account still backfilling or failing reconciliation (rows are missing). The raw per-leg feed stays behind a "Transfer legs" toggle on the same tab (it is the only in-context place to ignore a token); the ledger's row detail fetches those legs via `GET /api/eth/transfers?tx_hash=&chain_id=`.
- **Exchange matching** (migration 041, `services/ExchangeMatchService.js` + `models/ExchangeMatch.js`, `GET /api/exchanges/matches`): "sent 1.4 ETH to Coinbase" (on-chain) and "Coinbase received 1.4 ETH" (a record) are ONE event seen twice, so `exchange_matches` says they are the same money. DERIVED WHOLESALE like `eth_activity` itself — the pass runs at the END of `EthActivityService.rebuildForWallet` (and after CSV import, API sync, and account delete), because `eth_activity` is delete-then-insert and `activity_id`'s CASCADE means a match written earlier is already gone. Scoped to the USER, never the triggering wallet: matching is a one-to-one claim over a shared pool of records, so a per-wallet pass would let whichever wallet rebuilt last steal a record from the first. One table holds two shapes (`activity_id` + record, or record + `counter_record_id` for a Coinbase→Kraken transfer that never touched a tracked wallet), enforced by a `one_shape` CHECK; three unique indexes make one movement count once. **Evidence order is the algorithm** — selection is greedy, and the comparator's keys in order are `manual` first, then SHAPE (an on-chain candidate before an exchange pair), then `tx_hash` → `address_amount` → `amount_window`, then time delta and ids. Shape is an explicit key, not a by-product of the ranks: both shapes carry the same ranks, so leaving it implicit let an equal-rank (or merely closer) pair steal the record from the real on-chain leg — "no tracked wallet in between" is exactly what makes a pair a pair. Ranking shape above evidence costs the hash rule nothing, because the two cannot collide: a pair reaches `tx_hash` only when BOTH its records carry a hash, and a record carrying a hash produces no sub-hash on-chain candidate at all (the fallback arm requires `tx_hash IS NULL`). Verdicts live in `exchange_match_verdicts` — `rejected` suppresses, `confirmed` re-creates — keyed on `(wallet_id, chain_id, tx_hash)` and NOT on `eth_activity.id`, because that surrogate churns on every rebuild. **Traps**: (1) `exchange_records` has no chain column while `eth_activity` is chain-keyed (039), so a stored hash is chain-AMBIGUOUS — treated as identity anyway, since a 32-byte hash is not reproduced by accident and a genuine cross-chain replay is the same account's own money either way; (2) every amount comparison is exact NUMERIC (`ABS(record − leg) <= fee + leg * 0.005`), never float — these are wei-scale quantities — and the `fee` term is `base_fee_amount`, zero unless `fee_asset` IS the base asset: Coinbase retail books a withdrawal fee in USD, and adding "12.34" to a tolerance measured in ETH matched a 3.5 ETH transfer against a 2 ETH record. A foreign-currency fee gets the 0.5% relative slack and nothing else; (3) direction is enforced on both arms (on-chain `exchange_deposit` ⇒ the venue recorded a `deposit`), or a deposit and a withdrawal of the same size on the same day match each other; (4) the fallback arm requires exactly ONE net leg and an already-`exchange_*` category, so it cannot invent pairings for arbitrary sends; (5) the learning loop writes an `eth_address_labels` row (`source='auto-match'`, `confidence='low'`) ONLY from a hash match whose activity has exactly ONE net leg (with several, `counterparty_address` is the gas leg's `to_address` — a router contract, and labelling that `exchange` deletes every future call to it from cash flow) and ONLY when the address has no verdict of any kind — user or global — which is how precedence holds without this knowing the precedence rules; it heals FUTURE classification and never re-enters the rebuild that called it; (6) unmatched exchange flows get `needs_review`, gated on the user holding at least one deposit/withdrawal record anywhere — not on a time window over those records, which looked tighter and quietly broke the delete-the-account case by shrinking the covered period past the transfer it had just unexplained; (7) `exchange_records.needs_review` is never written here — it is 037's one-way upgrade gate, and a derived pass must not be able to close it, so record-side gaps are reported as a count instead; (8) all three category readers (candidates, the flag pass, the summary) COALESCE the override over the derived category, or a transaction corrected AWAY from an exchange flow generates no candidates and is then flagged for having none — a review nothing can satisfy; (9) `clearReviewForMatched` stamps the match's confidence on every matched row, not only on flagged ones, so the stored answer does not depend on whether the transfer was synced before or after its record was imported; (10) the verdict statements gate the WALLET as well as the record (the record's account says nothing about the bound `wallet_id`), and a second `confirmed` verdict claiming a record another confirmation already claims is a 409 — the two sit under different unique keys, so the database takes both and the selection pass would silently drop one. The match pass is user-wide, so a caller walking every wallet of one user passes `rebuildForWallet(id, { rebuildMatches: false })` and runs it once after the loop. **Deferred**: asset comparison is raw symbol equality (WETH/stETH false negatives; a spoofed ticker a false positive, mitigated only by the fallback arm needing an exchange label).
- **Historical USD valuation** (migration 043, `services/HistoricalPriceService.js` + `models/AssetPriceHistory.js`, `jobs/historicalPriceJob.js` at 8:10 UTC): the on-chain USD figures used to come from a CURRENT price, so a 2017 half-ETH send read as today's ~$1,800 instead of the ~$150 it was. `asset_price_history` is a dated series (asset_key, price_date, price_usd NUMERIC) — shared/global with no user column, like `benchmark_prices` and `price_cache`; valuations still flow through user-scoped reads. The asset key is `'ETH'` (native, every chain) or `erc20:<chain_id>:<contract>` — never a ticker, and chain-scoped because the same address is a different asset per chain (039); `utils/assetPriceKey.js` and `AssetPriceHistory.assetKeySql()` are the JS and SQL halves and must agree. **Sources, probed live**: CoinGecko `/coins/{id}/market_chart/range` (https://docs.coingecko.com/reference/coins-id-market-chart-range) is first — daily granularity above a 90-day span, one call per window — but a public/demo key answers **HTTP 401 error_code 10012** for anything older than 365 days, so ETH falls back to **Coinbase Exchange `/products/ETH-USD/candles`** (https://docs.cdp.coinbase.com/exchange/reference/exchangerestapi_getproductcandles), keyless, `granularity=86400`, **max 300 candles per request**, history from 2016-05-18 — that fallback is what makes 2017 dollars reachable on a free key. Tokens have only CoinGecko's contract endpoint, against that chain's `coingeckoPlatform`; a wrong platform is a 404. Throttling is **per provider**, process-wide (same shape as `config/etherscan.js`, not the same spacing): CoinGecko 2100 ms (demo = 30 calls/min; a shared 250 ms queue was 240/min, so a 200-asset budget 429'd everything past the first thirty, the same thirty every night), 250 ms on a pro key and on Coinbase. Tier is DECLARED, not sniffed — `CG_API_PLAN=pro` switches host AND header together (`pro-api.coingecko.com` + `x-cg-pro-api-key`; demo is `api.coingecko.com` + `x-cg-demo-api-key`), because a key sent under a header the host does not read is ignored in silence and the call runs anonymous. `utils/coingecko.js` owns both halves and `PriceService` goes through it. **HTTP 429 is a verdict on the RUN, not the asset**: the CoinGecko queue shuts for the rest of the run and the affected assets get NO coverage row, so they stay due (writing `error` would invent a verdict and refresh `checked_at`, making a run that died at asset 31 look like one that examined all 200). **Daily convention**: the stored price for date D is the LAST observation inside D (UTC) — CoinGecko's daily points are 00:00 UTC snapshots, Coinbase's candle close is D's close. **The valuation is ONE SQL statement** (`AssetPriceHistory.applyToWallet`, exact NUMERIC, clamped so a scam-token price cannot abort the pass) that denormalizes `usd_at_time` + `usd_basis` onto `eth_transfers`, the same derive-and-replace idiom as `counterparty_exchange`; the mirror and `eth_activity` READ those columns and price nothing themselves — which is what makes rebuilds byte-identical and let `EthTransactionMirrorService` drop its CoinGecko call, TTL cache and stale-amount fallback entirely. `usd_basis` is `exact` | `carried` (newest close within `MAX_CARRY_DAYS`=7, forward only — never backward, never from today) | `unpriced` (NULL usd, never $0) | `not_applicable` (NFT legs, whose `value_wei` is a unit count, and reverted transfers). `eth_activity` rolls up `usd_value` (ONE side — a 1-ETH-for-3000-USDC swap is a $3,000 event), `usd_fee`, `usd_basis` (weakest across the legs), netting in INTEGER CENTS. **An unpriced leg is NOT mirrored into `transactions` at all** — not at $0.00. `transactions.amount` is what Spending sums and the table carries no basis column, so a mirrored row IS an assertion about dollars; a 2019 500-USDC deposit outside a free key's token range would otherwise delete $500 from Spending as a real zero. Gas legs follow the same rule. The activity is still explained by `eth_activity.usd_basis`, the transfers feed's "No USD value", and the unpriced enumeration; the mirror is rebuilt wholesale, so a leg priced by a later backfill reappears. `asset_price_coverage` remembers each provider verdict so a dead EtherDelta-era token is not re-probed nightly: `unlisted` (404) and `empty` (a clean 200 with no closes) are both re-checked after 30 days, `range_limited` now also covers a series that merely stops short of the dates the ledger needs (compared against the requested window start — a non-empty array is not a covered window), and `covered` whose `latest_date` is already yesterday is skipped for the run. The due list is ordered by STALENESS (`checked_at` oldest first), not by the work list's transfer count: a stable ordering plus a budget slice starved the tail permanently. It backs `GET /api/eth/prices/unpriced`, the enumeration that keeps "unpriced" honest (no UI consumer until #63's unified ledger). **Traps**: (1) `null`/`''` coerce to 0 through `Number()`, so the daily fold rejects them by identity or a reported gap becomes a fabricated $0 close; (2) an off-shape 200 is a transient error, never a cached "no series" — same rule as the Sourcify decode; (3) the job runs at 8:10, AFTER the ETH sync at 7:50, so today's new transfers and newly-seen tokens are in the work list; a wallet's own sync also fills its assets (budget 25) so a freshly added wallet is not a screen of "No USD value" — but ONLY on a wallet add or a user-pressed Sync (`syncWallet(id, { fillPrices })`, default true; `syncAllWallets` defaults it FALSE), because the nightly job would otherwise walk the same providers under the same rate limit twenty minutes before the price job does. The SQL re-valuation runs on every sync either way: it touches no network; (4) `usd_volume` in the counterparty triage queue now weighs at-the-time dollars, which is the point — old ETH flows stop outranking this year's.
