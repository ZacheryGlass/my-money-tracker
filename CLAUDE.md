# CLAUDE.md

## Project Overview

**my-money-tracker** — personal portfolio tracker. Node.js/Express backend, React/Vite frontend (JSX, not TypeScript), PostgreSQL, Tailwind CSS 4. Multi-user with fully isolated data: production auth is Azure App Service Easy Auth with Google sign-in (identity read from `x-ms-client-principal-*` headers, gated by `ALLOWED_PRINCIPALS`); an allowlisted email's first sign-in auto-provisions a user via `user_identities` (one person can map several emails to one user — both of the original owner's emails point at user 1). Local dev stubs identity (`DEV_AUTH_USER_ID`/`DEV_AUTH_USERNAME`; the stub ensures the users row exists, so `DEV_AUTH_USER_ID=2` simulates a second user). `/mcp` is protected by an `MCP_API_KEY` bearer token that maps to user 1; `FinancialQueryService` methods all REQUIRE a userId and throw without one.

## Quick Start

```bash
# First time: bootstrap DB, .env files, deps, migrations (migrations seed user 1)
./scripts/setup-local.sh    # run in Git Bash (not WSL)

# Start both servers (double-click or run from any terminal)
python scripts/dev.py       # backend :3000, frontend :5173/private/

# No login locally; dev identity is stubbed in backend/src/middleware/auth.js
```

## Architecture

- **Backend**: Express 5, CommonJS, pino logging, pino-http request IDs, express-rate-limit, node-cron scheduled jobs
- **Frontend**: React 19, Vite 7, Tailwind CSS 4, Recharts (all charts), TanStack Table, React.lazy code splitting
- **Design**: "AVE Workbench" — VSCode-inspired dark workbench. CSS custom properties in `index.css`, mapped to Tailwind via `tailwind.config.js`. System fonts (UI) + Consolas (financial numbers). Primary: #297AA0, canvas: #191A1B, editor: #121314. Dense 13px UI, 1px borders, square panels. See `DESIGN.md` for full spec.
- **Layout**: Sidebar navigation (not top nav), state-based routing (no React Router in production)
- **Serving**: backend serves `backend/public/` (public landing) at `/` and the built React app at `/private` (Vite `base: '/private/'`). Azure Easy Auth gates `/private` and `/api` in production; `/` and `/mcp` are excluded.

## Key Patterns

- **API interceptor** (`frontend/src/utils/api.js`): same-origin requests (Easy Auth session cookie), retries on 5xx (once, 500ms), reloads page on 401 so Easy Auth re-authenticates
- **Shared formatters** (`frontend/src/utils/format.js`): `formatCurrency`, `formatPercent`, `formatDateDisplay`, `formatDateAxis`, `formatCompactCurrency`, `formatRelativeTime` — all components import from here, no local duplicates. Category labels in `utils/dataLabels.js`.
- **Shared UI**: `FilterTabs` (single-choice control — tab strip on desktop, dropdown on mobile, optional `{ divider, hint }` entries group the strip; PAGE-LEVEL MODE only: Balances, Settings and Crypto page tabs, plus Spending's View strip — the one entry that switches no URL, but it retitles the page and swaps the dataset the whole screen is about, which is what a tab strip means here; anything narrowing ONE table is a filter and uses `SegmentedControl`), `SegmentedControl` (labeled single-choice filter — segments on desktop, scrolling rather than clipping when a dynamic option set overflows; `mobile='segments'` stretches to equal parts, `mobile='select'` swaps in a labeled dropdown for option counts a phone cannot fit; `ariaLabel` instead of `label` when the surrounding row already names the control on screen, as Settings' appearance rows do. Every segmented filter uses this rather than a second tab strip: CryptoLedger's Show, OnChainActivity's Type, Accounts' type, Spending's account, Top Merchants' period, Settings' appearance rows via the `AppearanceOptions` adapter, and the chart range strips on Portfolio Timeline and Ticker History — a handful of single-choice filters are still plain `<select>`s, not tab strips: Balances' category/account, the Dashboard's account/range, Crypto's wallet. **Trap**: a `<select>` cannot host a TOGGLE — it can neither re-fire on the option already showing nor hold a value the parent declines — so Portfolio Timeline's Custom, which opens the date panel rather than naming a range, sits beside the control as its own button and the control parks on an empty value while a custom range is applied), `DataTable`/`DataTablePagination` (TanStack table shell — used by Balances, Accounts, Spending, Salary History, Holdings Analysis, Dashboard, Crypto, and both crypto feeds: OnChainActivity and CryptoLedger), `LoadingState` (all loading spinners), `useTransientMessage` (auto-clearing success messages)
- **Chart theme** (`frontend/src/utils/chartTheme.js`): `CHART_COLORS`, `GRID_STYLE`, `AXIS_STYLE`, `TOOLTIP_STYLE`, `areaGradient` — all charts use these
- **Design tokens**: CSS variables in `index.css` (canvas/surface hierarchy, ink/body/muted text, primary action blue, gain/loss semantics, hairline borders) consumed by Tailwind config. Component classes: `.card`, `.font-money`. Square panels with 1px borders, 4px radius on buttons/inputs only.
- **Crypto page tabs** (#75): everything that manages crypto lives on the Crypto page, not in Settings — Overview / Holdings / Transactions, then Wallets (add, sync, disconnect, balance audit), Exchanges (accounts, keys, CSV import), Review (unreviewed counterparties + quarantined spam) and Labels (address labels + ignored tokens). Each is a real URL (`/crypto/wallets`, …) registered in `App.jsx`'s navItems and `CRYPTO_TABS`; the panels live in `components/crypto/` and own their form state, while `CryptoPage` owns the data. The management lists are fetched by `fetchManageData` only when one of those tabs is first opened — Overview and the ledger need none of it — and every panel action calls `handleManageChanged`, which refetches BOTH halves and bumps `syncNonce`: a label write reclassifies the very rows the ledger is showing. Settings keeps Appearance, Data Tools, Institutions, API Keys, Accounts and Server.
- **Multi-user scoping**: ownership lives on root tables only (`accounts`, `plaid_items`, `eth_wallets`, `salary_history`, `recurring_expenses`, `ignored_merchants`, `eth_ignored_tokens`, `eth_address_labels` — nullable there, NULL = shared builtin). Children (holdings, transactions, snapshots, trades, tax lots, eth_transfers, …) inherit via `JOIN accounts a … AND a.user_id = $n`. Mutations use `WHERE id = $1 AND user_id = $2` → foreign ids 404. Scoped model reads are fail-closed (a missing userId throws); cross-user reads use the explicit `findAllForJobs` entry points (`Holding`, `EthWallet`, `PlaidItem`) and belong only to jobs. Shared/global by design: `price_cache`, `benchmark_prices`, `security_master`, `job_logs`, `eth_method_signatures`. Auth resolves users through `user_identities` with a 5-min in-process cache and auto-provisions allowlisted emails.
- **API keys** (Settings → API Keys, `routes/keys.js` + `services/SecretsService.js`): per-user Plaid client ID/secret and Etherscan key in `user_api_keys`; shared CoinGecko/CMC keys in `app_settings` (admin-only, managed from the Server tab). AES-256-GCM encrypted with `SECRETS_ENCRYPTION_KEY` (32-byte base64); resolution is DB value → env var → null; masked statuses only ever reach the client (stored `last4`). Without `SECRETS_ENCRYPTION_KEY` the app is env-only and key writes 503. Plaid clients come from `config/plaid.js` `getPlaidClientForUser`; Etherscan keys are threaded through `EtherscanService` per request.
- **Admin panel** (Settings → Server tab, `routes/admin.js`, gated by `requireUser.requireAdmin`): user 1 is the sole admin (`users.is_admin`, seeded by migration 030, no grant UI). Shows shared market-data keys, an env overview (secrets as masked last-4 only — full values never leave the server, and `SECRETS_ENCRYPTION_KEY` reports set/valid with no last-4 at all), a view-only users list, job schedules with Run Now buttons, and health. Tab visibility comes from `/api/me`'s `isAdmin`, not from probing the admin API. Non-admins never see the tab and get 403 from `/api/admin/*` and from shared-key writes.
- **Scheduled jobs**: Plaid sync 7:30, expense sync 7:45, ETH wallet sync 7:50, exchange API sync 7:55, price updates 8:00, historical price backfill 8:10, benchmark prices (SPY/QQQ) 8:30, snapshots 9:00 (all UTC). Controlled by `RUN_SCHEDULED_JOBS`. Plaid/eth/exchange syncs resolve each item/wallet/account OWNER's credentials and skip-and-log unconfigured owners; expense sync iterates users; price/benchmark/snapshot jobs stay global. `POST /api/jobs/trigger/*` is admin-only (these jobs touch every user's data with each owner's credentials) except `price-update`, which any user may run because `price_cache` is shared and the Dashboard refresh calls it.
- **Ethereum wallets**: Etherscan V2 integration mirrors the Plaid shape (`services/EthWalletService.js`, `routes/eth.js`, `jobs/ethSyncJob.js`). Raw transfers land in `eth_transfers` (counterparty classified self/exchange/external — both sets scoped to the wallet OWNER: self from the owner's wallets UNION their `kind='own'` labels, exchange from the owner's `kind='exchange'` labels plus shared builtins seeded in migration 029, user label shadows builtin, own beats exchange), balances become a `crypto` account with an ETH holding + NULL-ticker token holdings, and activity is mirrored into `transactions` via `eth_transfer_id` with `CRYPTO_*` categories (`CRYPTO_EXCHANGE_DEPOSIT`/`_WITHDRAWAL` classify as internal transfers). Token symbols never enter `price_cache`. A txlist row's `methodId`/`functionName` ride on exactly one leg per tx: the native leg when ETH moved, else the gas leg (zero-value calls -- approve, token swaps -- emit no native leg but their calldata still originated from the wallet); the reshaped classic-era Arbitrum credit (039 bullet) is the one INBOUND native leg that can carry a method — its calldata was the depositor's, served on the same txlist row. Selectors Etherscan cannot name are decoded during sync (never at request time, bounded by a lookup cap and a 30s deadline) via Sourcify's signature database, then 4byte.directory, cached in the global `eth_method_signatures` including MISSES so each selector is fetched at most once ever -- but an off-shape 200 counts as a transport failure, never a cached miss. A decoded name is a low-confidence display hint (selector collisions are mined deliberately) and must never feed classification. Method capture is FORWARD-ONLY: rows ingested before migration 034 keep NULL method columns (the decode pass names stored selectors, it cannot invent them); Wallets → Recapture re-fetches every enabled feed from genesis while preserving notes, labels, overrides, spam decisions, and reconciliation adjustments. Disconnecting with `removeData=false` detaches the account but keeps its row and name, so `addWallet` re-attaches (and un-hides) that account instead of inserting a duplicate — the account name is unique per user, and re-attaching is what preserves the history "keep data" was for.
- **NFT transfers** (migration 033): `tokennfttx`/`token1155tx` feeds land as `transfer_type` `nft`/`nft1155` legs carrying `token_standard` + `token_id`, with per-feed cursors (`last_block_nft`/`last_block_1155`, default 0 — so unlike FORWARD-ONLY method capture, 033 backfills NFTs from block 0 at the next sync). `value_wei` on NFT rows is a COUNT OF UNITS (always 1 for erc721 — the feed has no value field; the 1155 feed's `tokenValue`), never wei — a `/1e18` reader must branch on transfer_type first, and `token_decimals` is written 0 because the shared unit helpers default NULL to 18. Balance math stays fail-closed: `tokenBalanceDeltas` keys on `token_standard = 'erc20'`, so NFT legs can never leak into holdings. Feed failures are isolated per feed: a failed NFT fetch skips that feed's `deleteFromBlock` and leaves its cursor unmoved while the other feeds proceed — advancing past unfetched rows would drop them silently and forever. Etherscan emits one row per id for 1155 batches, so ordinals unbundle a batch with no extra work.
- **Exchange records** (Crypto → Exchanges, `routes/exchanges.js`, `services/exchangeImport/`, migrations 037 and 056): on-exchange activity never touches a tracked wallet, so it arrives as a CSV export. `exchange_accounts` is the root table (`user_id NOT NULL`); `exchange_records` inherits scope through it. One record per economic event, not per CSV line — Kraken's two trade legs (paired by `refid`) and Coinbase Pro's two `match` rows plus its `fee` row (grouped by order+trade id) each collapse into one row carrying both assets and the fee. `UNIQUE (exchange_account_id, external_id)` keys records by the event the exchange recorded, and the conflict arm is a one-directional guarded upgrade — `DO UPDATE … WHERE exchange_records.needs_review AND NOT EXCLUDED.needs_review` — so re-uploading the same export is pure duplicates while a FULLER export completes flagged placeholders without ever downgrading a complete row (in-file duplicates collapse first; Postgres refuses to update the same row twice in one statement). Resolving a review is a one-way door: it clears `needs_review`, which is the upgrade gate, so a hand-resolved partial row is "accepted", not "repairable". Rows with no native id (Coinbase Pro conversions) get a deterministic content hash. Upload is raw `text/csv`, like the holdings bulk import. **Fail-closed both ways**: an unrecognized header layout aborts the whole import with the header quoted back, and an unrecognized ROW type imports as `record_type='transfer'` with `needs_review` — never dropped, and never guessed into income or a deposit (which would enter the on-chain matching pass). Migration 056 adds nullable source-backed `network` and normalized `chain_id` fields; API/CSV network values are preserved while unknown or non-EVM networks remain NULL, and matching narrows only when a chain is proven. Two Kraken traps: `earn` rows with subtype `allocation`/`autoallocation` are spot↔earn wallet moves, not rewards (booking them as income would count the whole allocated principal, twice), and asset codes need normalizing (`XETH`→ETH, `ZUSD`→USD, `ETH2`→ETH, `.S`/`.M`/`.F` suffixes stripped) or one position splits in two. Fixtures under `backend/tests/fixtures/exchanges/` are synthetic by rule — real exports are personal history and the repo is public.
- **Exchange record dedupe** (#81, migration 062, `services/exchangeImport/canonicalFingerprint.js` + `models/ExchangeRecord.js`): `external_id` remains the exact provider replay key, while the provider-aware SHA-256 fingerprint is a non-unique same-day candidate key over normalized event type, asset legs and fee. Only one high-confidence API↔CSV candidate with matching full timestamp and no conflicting hash/address/network/chain details is collapsed; incoming raw/source details are appended to `dedupe_provenance` and `exchange_record_dedupe_events`. Same-source, same-day, or conflicting candidates remain separate, flagged, and reviewable. Historical rows are not merged by migration; `scripts/report-exchange-duplicates.js` is the read-only dry-run report for those rows.

- **Counterparty triage** (Crypto → Review → Needs Review, `GET /api/eth/counterparties/unreviewed`): `eth_address_labels.kind` (migration 032) makes a label mean "reviewed, with a verdict" rather than "is an exchange" — `exchange` | `external` (reviewed third party, changes nothing) | `own` (the user's untracked address; strictly user-scoped, no builtin fallback) | `bridge` (044, see below) | `service` (046: an instant-swap deposit address — Changelly, ShapeShift — where value sent was DISPOSED OF and what came back is not on this chain to find; ladder rung 3b classifies it `exchange_trade`, unflagged, since unlike a bridge there is no far side to wait for. It exists because the two alternatives are both wrong: `exchange` books a disposal as an internal transfer and deletes it from the record, `external` leaves every transfer flagged as possible spending. Delivered as a resolved address Set like `bridge`, NOT denormalized — `counterparty_exchange` doubles as the internal-transfer assertion. Inserted as "3b" rather than renumbering: rules 1-8 are cited by number across the services, tests and this file). The queue is every counterparty with no label row of any kind, minus gas rows, failed transfers, own counterparties, ignored-token transfers, quarantined-spam transfers (045) and contract creations — so it drains monotonically; a static hot-wallet seed can't keep up with exchanges rotating addresses, and an unlabeled one silently reads as real spending. `EthWalletService.refreshClassificationsForUser()` re-derives that owner's rows, so labeling heals all history retroactively. Badge counts material rows only (`usd_volume >= min_usd OR sent_count_valued > 0`) — a badge that can't reach zero gets ignored, which is exactly why outbound NFT legs are excluded from that OR arm (038): an NFT leg gets no mirror row, so its `usd_volume` is 0 forever and the arm — which exists to rescue a value that merely FAILED to resolve — would pass permanently, making every one-time NFT buyer material at $0. `sent_count` still reports the true outbound count for display; NFT-only counterparties stay enqueued as dust (`include_dust=true`) and the transaction itself is explained in `eth_activity`. **Traps**: (1) in `reclassifyCounterparties`' second UPDATE, `kind` is tested in the projection CASE, never the WHERE — filtering there lets a builtin `exchange` outrank a user's `external` override; (2) `upsert` takes a NULL `kind` as "keep the current verdict" (defaulting to `exchange` only on insert), because a rename sends no kind and must not silently re-vote; (3) the queue orders `material DESC` before `usd_volume DESC`, or an unpriced outbound counterparty sorts below every one-cent airdrop and pages out from under its own badge.
- **Activity layer** (migration 038, `services/EthActivityService.js` — DB orchestration only since the split; the pure policy (ladder in `classify.js`, quarantine in `spam.js`, netting/row assembly in `legs.js`/`rows.js`, bridge pairing in `bridge.js`) lives under `services/ethActivity/` and is re-exported by the service byte-compatibly — + `models/EthActivity.js`, `GET /api/eth/activity`): `eth_transfers` is per LEG, so a swap reads as three unrelated ledger rows. `eth_activity` is the tx-level explanation — exactly one row per `(wallet_id, chain_id, tx_hash)`, enforced by a UNIQUE constraint — the builder groups legs on `(chain_id, tx_hash)`, never `tx_hash` alone, because a cross-chain replay (same account, nonce and calldata on two chains) genuinely shares a hash, with `legs JSONB` netted per asset and `fee_wei` off the gas leg. DERIVED WHOLESALE: rebuilt on sync and on every classification refresh (label write, wallet add/remove, ignore-list change), same pattern as `reclassifyCounterparties`. Corrections live in `eth_activity_overrides` — a separate table precisely so the rebuild cannot erase one — and every reader COALESCEs override over derived, which also clears `needs_review` (an override IS a review). The per-leg `transactions` mirror is untouched; Spending still reads it. **Ladder** (deterministic first): `is_error` → `failed` is evaluated as a GATE, not the numbered rule 8 — a reverted send to Coinbase would otherwise pass rule 2 as a completed deposit — then 1 all-own → `self_transfer`, 2 exchange label → `exchange_deposit`/`_withdrawal`, 3 bridge label → `bridge_out`/`bridge_in` (#59, always flagged until the far side matches), 4 zero-address NFT legs → `nft_mint`/`nft_burn`, 5 no net movement → `contract_interaction`, 6 fungible out + different fungible in → `swap`, 7 NFT vs fungible → `nft_purchase`/`nft_sale`, 8 one-way → `send`/`receive` with `needs_review` always true. **Traps**: (1) `method_id`/`method_name` are copied for DISPLAY only and NO rule reads them — which is why `approval` is unreachable from the ladder (only the selector separates it from any other zero-value call) and is override-only, alongside `spend`, which waits on a merchant label kind; (2) rule 8 never auto-classifies spending, so an unreviewed outbound transfer is flagged, never counted; (3) NFT legs net per `(contract, token_id)` and their `value_wei` is a UNIT COUNT (033), so `legDecimals` branches on `transfer_type` before scaling; (4) ignored-token legs are filtered out of classification, so spam lands as an unflagged `contract_interaction` instead of refilling the review queue nightly; (5) an unknown `?category=` or `?needs_review=` is a 400, not a silently unfiltered feed; (6) the revert gate reads `eth_transfers.tx_is_error` as well as per-leg `is_error` — a reverted ZERO-VALUE call (failed approve, swap that reverts before any Transfer log) emits only a gas leg, and gas legs are written `is_error = false` deliberately (the fee did not fail, and the mirror and triage queue depend on that), so 038 stamps the transaction's own status on the gas leg at ingest. FORWARD-ONLY like 034's method capture: pre-038 rows are NULL and still classify `contract_interaction`; use the safe Wallets → Recapture action to re-ingest from block 0; (7) an override must target an existing activity row — readers join activity → override, so a correction against an unseen hash would be stored and invisible forever, hence the 404.
- **Derived-rebuild pipeline** (`services/EthDerivedPipeline.js`): the ONE canonical step list for everything derived from `eth_transfers` — reclassify → value → holdings → mirror → activity → match → bridge → classification backfill — parameterized by `_syncWallet` (fatal-on-first-failure), the label/ignore refreshes (per-step isolation) and the nightly price job (which, hand-copied, once drifted and skipped the backfill). All rebuild work serializes on an in-process PER-USER lane (delete-then-insert rebuilds racing would corrupt derived rows; the old global queue also let one user's label write wait on another's block-0 sync), with a reserved `global:backfill` lane so the global classification backfill never overlaps itself. Routes still await rebuilds — the response IS the write barrier the UI's immediate refetch depends on. Pipeline steps resolve dependencies at CALL TIME off module objects (tests stub by property assignment; a destructured ref would bypass them — pinned by a late-binding test in `ethDerivedPipeline.test.js`).
- **Spam quarantine** (migration 045, `detectSpam` in `services/ethActivity/spam.js`, `POST /api/eth/activity/spam`, Crypto → Review → Quarantined): address poisoning, dust and scam airdrops get a verdict at classification time so the review queue stays drainable at full-history scale. **A FLAG BESIDE the ladder's verdict, never in place of it**: `eth_activity.spam` + `spam_reason` (a REASON CODE, unlike `review_reason`'s prose — the poisoning warning has to render differently and a client can't branch on a sentence), with the category, legs, `usd_value` and `fee_wei` all untouched, and `eth_transfers` not touched at all, so #62's balance audit still derives from every wei that moved. `needs_review` also keeps the LADDER's answer and is masked at read time, so un-quarantining a false positive returns it to the queue instead of silently marking it reviewed. Reversible through `eth_activity_overrides.spam` (NULL = no opinion, FALSE = one-click un-spam, TRUE = hand-quarantine); **naming a category also lifts it** (`upsertOverride` writes `spam = FALSE`), because a quarantine says "you need not look at this" and the user saying what it was settles that the other way — leaving the flag up made a correction stored, acted on by the exchange matcher, and invisible behind its own mask. The counterparty triage queue excludes quarantined legs in its `legs` CTE (so neither the badge, `usd_volume` nor `sent_count` counts them) resolving `COALESCE(ovr.spam, act.spam)`, and `GET /api/eth/activity` defaults to `spam=exclude` (`only`/`all` also accepted; anything else 400s) while always reporting `summary.spam_count`, scoped to the same `wallet_id` as the feed — hiding rows without saying how many, or saying how many on some other wallet, is the one thing a quarantine may not do. **Gates run before any heuristic, and each is a promise**: a category asserting real money moved (`NEVER_SPAM_CATEGORIES`), `failed`, **the wallet signed the transaction**, any net outflow, a counterparty with any verdict, and finally **any priced inflow at or above $1**. Then, in order: (1) `address_poisoning` — a counterparty matching the first/last four hex of an address the OWNER declared theirs (every tracked wallet plus their `own` labels, passed in rather than inferred from `counterparty_is_own`, which only appears on transfers BETWEEN two of them) or that this wallet has deliberately paid, and only when nothing moved (asked over EVERY value leg, not just the inbound ones, so it reads correctly for the outbound spoof and never leans on a vacuous `[].every()`), or EVERY inbound leg carries a price and the total was under a dollar (every one, not merely one of them — five cents of priced junk beside an unpriced 2 ETH leg says nothing about the ETH, and the shared dollar gate cannot catch it because being under a dollar is what makes the junk leg worth sending), or EVERY arriving asset is one the wallet never voluntarily touched AND the provider has said outright has no market — 4+4 hex is 32 bits of coincidence and the cost of being wrong is hiding a payment, so an UNPRICED ETH transfer from a lookalike stays (no price means unknown size, not small); (2) `zero_value_transfer` — every leg exactly zero, the only "always" rule, since there is no financial content to hide; (3) `unsolicited_nft` and (4) `unsolicited_token` — EVERY arriving asset is a contract the wallet has never touched voluntarily (a native leg has no contract, so an ETH credit can never qualify), and for the token, nothing arriving carries a price and every arriving asset is one `asset_price_coverage` marks `unlisted`/`empty`. The accepted cost, stated so it is a decision: a scam airdrop bundled with a little ETH is NOT quarantined, because letting it through would mean deciding an unpriced ETH credit is small. **Traps**: (1) no rule reads `method_id`/`method_name`, same standing decision as the ladder — the selector is attacker-chosen; (2) `from_address` on a `token`/`nft` leg is copied out of a Transfer EVENT that any contract may forge, so only `native`/`internal` legs count as a signature (`SIGNED_LEG_TYPES`) and only a SIGNED transaction marks a contract voluntary — the fake-token variant emits `Transfer(victim, lookalike, 1000e6)` from a counterfeit USDT, and trusting it would both switch off every heuristic for that transaction and whitelist the counterfeit forever. Its own transaction still nets outbound and is therefore NOT quarantined -- the net-outflow gate is REACHABLE precisely by a forged leg, and letting it through is deliberate: from one wallet's feed a forged nonzero Transfer is indistinguishable from a real one on a chain whose `normal` feed is unsupported (039), and hiding a real outbound transfer is the worse error; (3) pricedness is read PER LEG off the netted inflows, never off `usd_value` — `rollUpUsd` folds to the weakest basis, so one unpriced junk leg makes the whole transaction report unpriced, and reading that as "no market, therefore not a payment" would let a scam leg supply its own evidence and take the ETH beside it into the quarantine. "Unpriced" is not "no market" either -- a leg is unpriced whenever the dated series does not reach it, which is true of every 2019 transfer until the backfill arrives -- so the rules that lean on worthlessness require the provider's own `unlisted`/`empty` verdict from `asset_price_coverage`, and a fresh wallet quarantines nothing under them until the price job has reported (fail-safe, a night at most). A leg that claims a price and will not parse stops the quarantine outright rather than counting as zero; (4) heuristics read WALLET-WIDE evidence built once per rebuild (`spamContext`), like `tokenDecimalsFallbacks`; (5) "already judged" must match the triage queue's answer, so the label read is the user's own rows PLUS builtin rows bounded to this wallet's counterparties — materialized ONCE per rebuild (a UNION CTE probed by hash) and served by 045's `(wallet_id, from_address)`/`(wallet_id, to_address)` indexes, because the correlated-EXISTS form ran the subquery once per pack row and measured 16.9s on a 30k-transfer wallet inside a rebuild that `routes/eth.js` awaits on every label write and ignore toggle — `exchange`/`own` arrive denormalized on each leg but `external` is inert in classification, and 036 ships 389 `external` payment processors and on-ramps; (6) a claimed airdrop (ENS) is never spam because signing it trips the signature gate, but it still classifies `receive` + `needs_review`, NOT `airdrop` — an inbound-only arrival in a signed tx is equally a vesting release or a DeFi withdrawal, and rule 8 exists so that stays a human's call; (7) an ignored token is not re-quarantined (its legs are filtered out before classification) and the automatic quarantine never writes to `eth_ignored_tokens`, because ignoring a token DOES remove it from balance derivation and reconciliation would then report drift the chain does not have; (8) `DELETE /api/eth/activity/override` drops BOTH verdicts (they are one row) and says so in its response, since re-hiding a rescued transaction as a side effect of a category action would be the rescue undone in silence.

DERIVED WHOLESALE like `eth_activity` itself — the pass runs at the END of `EthActivityService.rebuildForWallet` (and after CSV import, API sync, and account delete), because `eth_activity` is delete-then-insert and `activity_id`'s CASCADE means a match written earlier is already gone. Scoped to the USER, never the triggering wallet: matching is a one-to-one claim over a shared pool of records, so a per-wallet pass would let whichever wallet rebuilt last steal a record from the first. One table holds two shapes (`activity_id` + record, or record + `counter_record_id` for a Coinbase→Kraken transfer that never touched a tracked wallet), enforced by a `one_shape` CHECK; three unique indexes make one movement count once. **Evidence order is the algorithm** — selection is greedy, and the comparator's keys in order are `manual` first, then SHAPE (an on-chain candidate before an exchange pair), then `tx_hash` → `address_amount` → `amount_window`, then time delta and ids. Shape is an explicit key, not a by-product of the ranks: both shapes carry the same ranks, so leaving it implicit let an equal-rank (or merely closer) pair steal the record from the real on-chain leg — "no tracked wallet in between" is exactly what makes a pair a pair. Ranking shape above evidence costs the hash rule nothing, because the two cannot collide: a pair reaches `tx_hash` only when BOTH its records carry a hash, and a record carrying a hash produces no sub-hash on-chain candidate at all (the fallback arm requires `tx_hash IS NULL`). Verdicts live in `exchange_match_verdicts` — `rejected` suppresses, `confirmed` re-creates — keyed on `(wallet_id, chain_id, tx_hash)` and NOT on `eth_activity.id`, because that surrogate churns on every rebuild. **Traps**: (1) `exchange_records` has no chain column while `eth_activity` is chain-keyed (039), so a stored hash is chain-AMBIGUOUS — treated as identity anyway, since a 32-byte hash is not reproduced by accident and a genuine cross-chain replay is the same account's own money either way; (2) every amount comparison is exact NUMERIC (`ABS(record − leg) <= fee + leg * 0.005`), never float — these are wei-scale quantities — and the `fee` term is `base_fee_amount`, zero unless `fee_asset` IS the base asset: Coinbase retail books a withdrawal fee in USD, and adding "12.34" to a tolerance measured in ETH matched a 3.5 ETH transfer against a 2 ETH record. A foreign-currency fee gets the 0.5% relative slack and nothing else; (3) direction is enforced on both arms (on-chain `exchange_deposit` ⇒ the venue recorded a `deposit`), or a deposit and a withdrawal of the same size on the same day match each other; (4) the fallback arm requires exactly ONE net leg and an already-`exchange_*` category, so it cannot invent pairings for arbitrary sends; (5) the learning loop writes an `eth_address_labels` row (`source='auto-match'`, `confidence='low'`) ONLY from a hash match whose activity has exactly ONE net leg (with several, `counterparty_address` is the gas leg's `to_address` — a router contract, and labelling that `exchange` deletes every future call to it from cash flow) and ONLY when the address has no verdict of any kind — user or global — which is how precedence holds without this knowing the precedence rules; it heals FUTURE classification and never re-enters the rebuild that called it; (6) unmatched exchange flows get `needs_review`, gated on the user holding at least one deposit/withdrawal record anywhere — not on a time window over those records, which looked tighter and quietly broke the delete-the-account case by shrinking the covered period past the transfer it had just unexplained; (7) `exchange_records.needs_review` is never written here — it is 037's one-way upgrade gate, and a derived pass must not be able to close it, so record-side gaps are reported as a count instead; (8) all three category readers (candidates, the flag pass, the summary) COALESCE the override over the derived category, or a transaction corrected AWAY from an exchange flow generates no candidates and is then flagged for having none — a review nothing can satisfy; (9) `clearReviewForMatched` stamps the match's confidence on every matched row, not only on flagged ones, so the stored answer does not depend on whether the transfer was synced before or after its record was imported; (10) the verdict statements gate the WALLET as well as the record (the record's account says nothing about the bound `wallet_id`), and a second `confirmed` verdict claiming a record another confirmation already claims is a 409 — the two sit under different unique keys, so the database takes both and the selection pass would silently drop one. The match pass is user-wide, so a caller walking every wallet of one user passes `rebuildForWallet(id, { rebuildMatches: false })` and runs it once after the loop — `EthDerivedPipeline` owns that walk and its tail. **Deferred**: asset comparison is raw symbol equality (WETH/stETH false negatives; a spoofed ticker a false positive, mitigated only by the fallback arm needing an exchange label).
- **Historical USD valuation** (migration 043, `services/HistoricalPriceService.js` + `models/AssetPriceHistory.js`, `jobs/historicalPriceJob.js` at 8:10 UTC): the on-chain USD figures used to come from a CURRENT price, so a 2017 half-ETH send read as today's ~$1,800 instead of the ~$150 it was. `asset_price_history` is a dated series (asset_key, price_date, price_usd NUMERIC) — shared/global with no user column, like `benchmark_prices` and `price_cache`; valuations still flow through user-scoped reads. The asset key is `'ETH'` (native, every chain) or `erc20:<chain_id>:<contract>` — never a ticker, and chain-scoped because the same address is a different asset per chain (039); `utils/assetPriceKey.js` and `AssetPriceHistory.assetKeySql()` are the JS and SQL halves and must agree. **Sources, probed live**: CoinGecko `/coins/{id}/market_chart/range` (https://docs.coingecko.com/reference/coins-id-market-chart-range) is first — daily granularity above a 90-day span, one call per window — but a public/demo key answers **HTTP 401 error_code 10012** for anything older than 365 days, so ETH falls back to **Coinbase Exchange `/products/ETH-USD/candles`** (https://docs.cdp.coinbase.com/exchange/reference/exchangerestapi_getproductcandles), keyless, `granularity=86400`, **max 300 candles per request**, history from 2016-05-18 — that fallback is what makes 2017 dollars reachable on a free key. Tokens have only CoinGecko's contract endpoint, against that chain's `coingeckoPlatform`; a wrong platform is a 404 — except a declared ALIAS (`config/tokenPriceAliases.js`, validated at require time — a checksummed key, a bad `t…` symbol or a non-ISO historyStart throws at boot instead of failing silently nights later): a token CoinGecko can never price skips the contract endpoint for a keyless Bitfinex daily series under its own 2100 ms throttle (the candles route is ~30 req/min, CoinGecko-demo sized; a Bitfinex 429 pauses that queue for the run and writes no coverage row, same as CoinGecko's), same asset key, venue close treated as USD, ledger dates before the venue's first candle honestly `range_limited` — and zero candles over a window that includes the declared historyStart is a transient `error`, never `empty`, because the live venue answers 200 [] for an unknown symbol and an `empty` verdict feeds the spam quarantine's unlisted/empty set; one entry, the 2017-18 EOS ERC-20 via tEOSUSD (daily from 2017-07-01) — chosen by live probe, since Binance's public host serves EOSUSDT only from 2018-05-28 and its main host is region-blocked. Throttling is **per provider**, process-wide (same shape as `config/etherscan.js`, not the same spacing): CoinGecko 2100 ms (demo = 30 calls/min; a shared 250 ms queue was 240/min, so a 200-asset budget 429'd everything past the first thirty, the same thirty every night), 250 ms on a pro key and on Coinbase. Tier is DECLARED, not sniffed — `CG_API_PLAN=pro` switches host AND header together (`pro-api.coingecko.com` + `x-cg-pro-api-key`; demo is `api.coingecko.com` + `x-cg-demo-api-key`), because a key sent under a header the host does not read is ignored in silence and the call runs anonymous. `utils/coingecko.js` owns both halves and `PriceService` goes through it. **HTTP 429 is a verdict on the RUN, not the asset**: the CoinGecko queue shuts for the rest of the run and the affected assets get NO coverage row, so they stay due (writing `error` would invent a verdict and refresh `checked_at`, making a run that died at asset 31 look like one that examined all 200). **Daily convention**: the stored price for date D is the LAST observation inside D (UTC) — CoinGecko's daily points are 00:00 UTC snapshots, Coinbase's candle close is D's close, and Bitfinex's daily candle starts its MTS at D's UTC midnight with index 2 as D's close (verified live). **The valuation is ONE SQL statement** (`AssetPriceHistory.applyToWallet`, exact NUMERIC, clamped so a scam-token price cannot abort the pass) that denormalizes `usd_at_time` + `usd_basis` onto `eth_transfers`, the same derive-and-replace idiom as `counterparty_exchange`; the mirror and `eth_activity` READ those columns and price nothing themselves — which is what makes rebuilds byte-identical and let `EthTransactionMirrorService` drop its CoinGecko call, TTL cache and stale-amount fallback entirely. `usd_basis` is `exact` | `carried` (newest close within `MAX_CARRY_DAYS`=7, forward only — never backward, never from today) | `unpriced` (NULL usd, never $0) | `not_applicable` (NFT legs, whose `value_wei` is a unit count, and reverted transfers). `eth_activity` rolls up `usd_value` (ONE side — a 1-ETH-for-3000-USDC swap is a $3,000 event), `usd_fee`, `usd_basis` (weakest across the legs), netting in INTEGER CENTS. **An unpriced leg is NOT mirrored into `transactions` at all** — not at $0.00. `transactions.amount` is what Spending sums and the table carries no basis column, so a mirrored row IS an assertion about dollars; a 2019 500-USDC deposit outside a free key's token range would otherwise delete $500 from Spending as a real zero. Gas legs follow the same rule. The activity is still explained by `eth_activity.usd_basis`, the transfers feed's "No USD value", and the unpriced enumeration; the mirror is rebuilt wholesale, so a leg priced by a later backfill reappears. `asset_price_coverage` remembers each provider verdict so a dead EtherDelta-era token is not re-probed nightly: `unlisted` (404) and `empty` (a clean 200 with no closes) are both re-checked after 30 days, `range_limited` now also covers a series that merely stops short of the dates the ledger needs (compared against the requested window start — a non-empty array is not a covered window), and `covered` whose `latest_date` is already yesterday is skipped for the run. The due list is ordered by STALENESS (`checked_at` oldest first), not by the work list's transfer count: a stable ordering plus a budget slice starved the tail permanently. It backs `GET /api/eth/prices/unpriced`, the enumeration that keeps "unpriced" honest (rendered by `CryptoLedger` as a completeness signal beside the feed, so a gap in the series is visible rather than silently absent). **Traps**: (1) `null`/`''` coerce to 0 through `Number()`, so the daily fold rejects them by identity or a reported gap becomes a fabricated $0 close; (2) an off-shape 200 is a transient error, never a cached "no series" — same rule as the Sourcify decode; (3) the job runs at 8:10, AFTER the ETH sync at 7:50, so today's new transfers and newly-seen tokens are in the work list; a wallet's own sync also fills its assets (budget 25) so a freshly added wallet is not a screen of "No USD value" — but ONLY on a wallet add or a user-pressed Sync (`syncWallet(id, { fillPrices })`, default true; `syncAllWallets` defaults it FALSE), because the nightly job would otherwise walk the same providers under the same rate limit twenty minutes before the price job does. The SQL re-valuation runs on every sync either way: it touches no network; (4) `usd_volume` in the counterparty triage queue now weighs at-the-time dollars, which is the point — old ETH flows stop outranking this year's.
- **Bridge detection** (migration 044, `backend/data/builtin-bridge-labels.json` + `backend/scripts/generate-bridge-seed.js`, `models/EthActivityLink.js`): a bridge deposit is the user's own money changing chains, but the chains record it as two unrelated transactions — before this, the outflow fell to ladder rule 8 and was flagged as possible SPENDING. A fourth label kind `bridge` puts it on rung 3, and `eth_activity_links` pairs the two halves into one movement. 35 addresses seeded `source='builtin-bridge', kind='bridge', confidence='high'` (Arbitrum, Linea, OP, Base canonical bridges + Across SpokePools + Polygon PoS's RootChainManager and its Ether/ERC20 predicates — the PROXY addresses, which is what a user transacts with — plus Polygon's Plasma DepositManagerProxy and the MRC20 native precompile `0x…1010` (#76): POL bridges via PLASMA, not RootChainManager, so the L1 deposit's `to` is the DepositManager and the state-sync credit's `from` is the MRC20, which is why both are seeded 'bridge' — the L1 leg classifies `bridge_out`, the credit `bridge_in`, and the amount/time matcher pairs them (both symbols POL, 24h L1-out window) — plus the ArbRetryableTx precompile `0x…006e` on 42161, the `from` every reshaped classic-era deposit credit carries, so those credits classify `bridge_in` and pair against the already-seeded L1 Delayed Inbox leg), each read byte-for-byte out of raw first-party source and cross-checked against its explorer name tag; the source URL rides in the row's `note` (which renders as the label pill's tooltip) AND in the JSON — a per-entry `source_url` overrides the protocol source where the address lives on a different first-party page (the ArbRetryableTx precompile cites the precompiles reference, not the contract-addresses page), and the generator prefers it. Unlike the 036 pack these ARE listed in Settings — a few dozen rows where a wrong one has to be visible to be correctable. Matching is amount-and-time based, never address based: a fast-bridge fill arrives from the relayer, not the contract you deposited into. Cross-chain and cross-wallet, so it runs once per USER after the per-wallet rebuilds, and it is DERIVED (delete-then-insert), not a correction. **Traps**: (1) an unmatched bridge leg keeps `needs_review=true`, which is what makes a wrong bridge label cheap — it turns one flagged row into a differently-flagged row, the opposite of a wrong `exchange`, which silently deletes real spending from cash flow; (2) the re-flag direction is the load-bearing one: a rebuild of the wallet holding the far side cascades the link away (`ON DELETE CASCADE`), so a leg matched an hour ago must go back to flagged or it claims a transfer with nothing on the other end; (3) the match window is chosen by the chain the money LEFT — 24h from L1 (deposits land in minutes), 8 days from an L2 (the 7-day optimistic challenge period); (4) `WETH`→`ETH`, `MATIC`→`POL` (the Sept-2024 1:1 rename — pre-rename Plasma deposits carry `MATIC` on the L1 leg while `nativeSymbol(137)` is always `POL`) and a trailing `.e` (Arbitrum's bridged `USDC.e`) normalize, and nothing else does — every entry there asserts two symbols are the same money, and the rules COMPOSE (strip `.e` FIRST, then map the renames, or `WETH.e` gets a bucket of its own); (5) Hop and Stargate are deliberately NOT seeded: Hop publishes no addresses in its docs (only a moving SDK branch) and both protocols reuse one address for different contracts on different chains, which `eth_address_labels` (address-keyed, no chain column) cannot express — the user can label either in two clicks; (6) exactly one net fungible leg is required to pair, so a multi-asset bridge transaction stays flagged rather than guessed; (7) `legs[].asset` is a DISPLAY string and `'TOKEN'` is the placeholder for an ERC-20 the feed never named, so a leg carries `symbol_known: false` (emitted only when false, like `decimals_known`'s upgrade rule) and the matcher refuses it — two different unnamed tokens would otherwise compare equal and fuse; (8) both the matcher and `syncBridgeReviewState` filter on the RESOLVED category (`COALESCE(override, derived)`) like every other reader, so a bridge_out the user overrode to `send` gets no link and its far side goes back to flagged. **Scope boundary** (deliberate): only `exchange`/`own` are denormalized onto the leg, so bridge legs mirror into `transactions` as `CRYPTO_EXTERNAL`/`CRYPTO_TOKEN` — safe (never spending) but NOT recognized as an internal move the way `CRYPTO_EXCHANGE_DEPOSIT` is. The activity layer knows a bridge is one movement of the user's own money; the ledger mirror does not yet. **Known gap**: where a rollup credits the far side as an address-to-self system transaction rather than a transfer from the bridge contract, that leg classifies `self_transfer` (rule 1, already not spending) and stays unpaired. Polygon's native state-sync credit is the one such far side now ingested and paired (#76): it arrives FROM the MRC20 precompile, a seeded `bridge` counterparty, so it is `bridge_in` rather than a self-transfer. Other rollups' self-transaction credits remain the open case. One Bor quirk bounds the PAIRING, not the classification: a block's state syncs are bundled into ONE synthetic tx, so a wallet credited twice in the same bundle (a POL deposit beside a same-block token mint) gets a multi-leg `bridge_in` row that trap 6 refuses to pair — it stays flagged (the safe direction) until reviewed by hand; single-credit bundles, the common case, pair normally.
- **Forgotten-wallet discovery** (migration 057, `EthDiscoveryCandidate`, `EthDiscoveryService`, Crypto → Discovery): rerunnable one-hop value paths and exchange withdrawal destinations are persisted as `pending` evidence with source, score, chain id (0 means the source did not identify the chain) and JSON proof. A user can track a candidate, mark it owned-but-untracked, or dismiss it; confirmed/dismissed rows are never overwritten by a later seed. Candidate writes are user-scoped and discovery evidence is deliberately separate from ownership/classification labels. The current implementation covers proof-backed one-hop paths from already-ingested transfers and exchange withdrawals; bounded API expansion, multi-hop frontier traversal, contract/high-traffic/dust filtering, repeated census, and user confirmations remain open.
- **Migrations re-run on every boot** (no tracking table): every statement must be idempotent, constraint swaps need catalog-guarded DO blocks, and seeds live where their conflict targets exist (001's account seed and 026's builtin-label seed moved to 029). **When two migrations widen the SAME constraint, both must list the UNION of every value.** 041 and 044 each own `eth_address_labels_source_check` under their own sentinel; with narrower lists they took turns dropping and re-adding each other's, and once 044's `builtin-bridge` rows existed 041's re-add failed the CHECK — so every database booted once and then refused to boot again, while a fresh one looked perfectly fine. `verify-ledger-sql.js`'s second migration pass is what catches this.

The legacy explorer-log paginator likewise rejects a full page that cannot advance instead of stepping over an unknown tail. Each chain sync snapshots Blockscout's actual newest indexed height from `/api/v2/blocks` (not the potentially newer RPC head, and not `/api/v2/stats.total_blocks`, which is an aggregate count), bounds all six feeds at that common height and persists it as every successful feed's coverage even when the feed is empty; an empty wallet therefore never rescans genesis nightly or skips data the indexer has not reached. This closes the older bridge-detection paragraph's self-transaction gap for OP Mainnet and Base; other rollups remain a separate case.

- **Kraken asset aliases** (#79): the shared Kraken CSV/API normalizer first
  applies structural provider cleanup (legacy codes and single-letter wallet
  suffixes), then applies only explicitly verified economic aliases. `SOL03` and
  `SOL03.S` therefore become canonical `SOL`, while numbered tickers are never

- **Address notes** (migration 049, `eth_address_notes`, `GET|POST|DELETE /api/eth/address-notes`) are user-scoped prose, deliberately separate from `eth_address_labels`. The not-empty CHECK allows category, spam, or note; never UPDATE the final non-null field to NULL and then DELETE, because PostgreSQL checks the UPDATE before the DELETE runs.
